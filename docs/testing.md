# Сборка и тестирование

Нужны Docker Engine с Compose v2 либо Docker Desktop, интернет для скачивания зависимостей и возможность запускать Linux amd64. Все команды выполняются из корня репозитория. Проверки используют отдельную БД, синтетические материалы и изолированную сеть. API-ключи не требуются.

## Сборка

```bash
docker build --platform linux/amd64 --provenance=false --target checks -t aist-backend-checks:local -f infra/Dockerfile.backend .
docker build --platform linux/amd64 --provenance=false --target checks -t aist-web-checks:local -f infra/Dockerfile.web .
docker build --platform linux/amd64 --provenance=false --build-arg BACKEND_IMAGE=aist-backend-checks:local -t aist-native-checks:local -f infra/Dockerfile.openclaw .
```

Порядок важен: третий образ использует первый. Для сборки без кеша добавьте `--no-cache`.

Web-сборка выполняет проверку типов, тесты и production build. Backend устанавливает Python-зависимости с проверкой контрольных сумм, системные пакеты для DOCX/PDF и шрифты. Образ `aist-native-checks` добавляет установленный OpenClaw. Версии и зависимости закреплены в Dockerfile и lock-файлах.

## Автономные проверки

```bash
docker run --rm --platform linux/amd64 --network none aist-backend-checks:local
docker run --rm --platform linux/amd64 --network none --entrypoint python aist-backend-checks:local /workspace/contracts/v1/validate.py --package-only --manifest
docker run --rm --platform linux/amd64 --network none --entrypoint /opt/aist-openclaw/tools/node-v24.21.0/bin/node aist-native-checks:local --test /workspace/executor/openclaw/plugin/index.test.mjs
```

Первый запуск не подключает PostgreSQL. Тесты, которым нужна БД или отдельные пользовательские архивы, пропускаются по своим условиям. Статус `skipped` не означает успешную проверку. Пользовательские архивы в репозиторий не входят.

Валидатор проверяет схемы, примеры, связи между ними и целостность пакета контрактов. Он не запускает сервер и не заменяет интеграционные тесты.

## Сквозной сценарий с PostgreSQL и OpenClaw

```bash
docker compose -f infra/compose.checks.yaml up -d --wait db
docker compose -f infra/compose.checks.yaml run --rm checks
docker compose -f infra/compose.checks.yaml down
```

Проверка использует установленный исполнитель, локальный HTTP-сервер с синтетическими ответами и реальные миграции. Сценарии покрывают Astra с `xhigh`, историю и кеш вызовов, извлечение, исследование, сохранение, редакторскую правку и выпуск DOCX/PDF. Повторное скачивание проверяет неизменность файлов и отсутствие нового модельного запроса.

Compose создает проект `aist-checks`. Сеть имеет `internal: true`; контейнеры не получают API-ключей. База находится в tmpfs. Подсеть по умолчанию `10.253.241.0/28`; при конфликте задайте свободную через `AIST_TEST_SUBNET` и используйте то же значение при завершении.

Для дополнительных проверок адаптера MOEX на синтетических ответах:

```bash
docker compose -f infra/compose.checks.yaml up -d --wait db
docker compose -f infra/compose.checks.yaml run --rm checks python -m pytest -p no:cacheprovider tests/test_d16_postgres.py tests/test_d16_r1_postgres.py
docker compose -f infra/compose.checks.yaml down
```

Выполняйте `down` также после неудачного запуска. Не подключайте проверки к рабочей БД и не удаляйте чужие контейнеры или тома.

## Учет после ответа провайдера

`tests/test_received_response_postgres.py` требует изолированную PostgreSQL с миграциями и установленный OpenClaw. Выставьте `AIST_TEST_POSTGRES=true` и `AIST_TEST_OPENCLAW=true`. Набор использует внутренние HTTP-серверы с синтетическими ответами. Он проверяет учет после блокировки проекта, потерю подтверждения commit, остановку отправителя после сохранения ответа, конкуренцию и позднюю доставку, а также завершение веб-запроса без повторного обращения к провайдеру. Операторская сверка описана в [инструкции запуска](deployment.md#сверка-полученных-ответов).

Для проверки отказов провайдера и сверки расходов добавьте `tests/test_billing_reconciliation_postgres.py` к прогону с теми же флагами. Набор проверяет типизированные HTTP-отказы, учет и общий лимит, адресную CLI-сверку, конкуренцию, потерю подтверждения commit и восстановление сохраненного отказа на синтетических ответах. Отдельный тест запускает установленный OpenClaw. Ограниченный retry Novita проверяет `tests/test_perf02_r3_postgres.py`.

## Дополнительные сценарии

`tests/test_navigation_postgres.py` и `tests/test_chat_edits_postgres.py` используют изолированную PostgreSQL и `AIST_TEST_POSTGRES=true`. Они проверяют HTTP-курсор чатов, конкурентные решения, откат квитанции и повтор после потери ответа. Московская дата исследования проверяется также в `tests/test_openai_responses_postgres.py::test_installed_note_extracts_images_researches_saves_and_rewrites` с установленным OpenClaw и синтетическим провайдером.

Загрузку PDF проверяет `tests/test_pdf_upload_postgres.py` с изолированной PostgreSQL. Набор использует штатный API, пул из двух соединений и синтетические PDF. Он проверяет доступность API во время разбора, повтор по ключу, конфликт ревизий и восстановление результата commit.

На процесс API или worker выделено два общих слота подготовки PDF. В слот входят разбор, запись и fsync файла, атомарная публикация и проверка его содержимого. Во время этой работы соединение с БД свободно. При заполнении обоих слотов новая загрузка получает 503 `temporarily_unavailable`. Завершенный повтор проходит без слота и повторного разбора. Обрыв HTTP-соединения оставляет слот занятым до завершения подготовки.

Короткая финальная транзакция повторно проверяет права, ревизию и receipt, сверяет принадлежность файла и фиксирует версию. При потере подтверждения commit результат сверяется на новом соединении. Если исход установить не удалось, файл сохраняется и клиент получает `outcome_unknown`. Повтор использует тот же ключ.

Сбои API и worker проверяет `tests/test_failure_diagnostics.py`. Для полного набора нужна изолированная PostgreSQL и `AIST_TEST_POSTGRES=true`. Укажите тестовую БД с префиксом `aist_d15_r1_test` и роль с правом `CREATEDB`. Каждый сценарий создает отдельную БД, применяет миграции и удаляет ее. Тесты запускают Uvicorn на свободном loopback-порту, проверяют дочерний worker на сохраненном Run и читают фактический вывод процессов. Запросы к модели не выполняются. `tests/test_health.py` проверяет liveness для обоих режимов и безопасное тело readiness при отказе БД. Операторские команды приведены в [инструкции запуска](deployment.md#диагностика-api-и-worker).

Тесты backend находятся в `apps/backend/tests`, frontend в `apps/web/tests`, плагина в `executor/openclaw/plugin`. Материалы тестов описаны в [fixtures/README.md](../apps/backend/tests/fixtures/README.md).

Для адресной проверки HTTP-прокси из `apps/web` с зависимостями из lock-файла выполните `node --import tsx --test tests/proxy.test.ts`. Набор запускает штатный web-сервер и синтетический backend. Он проверяет GET и HEAD без тела, JSON и файловые загрузки через POST, заголовки и байты скачивания, отдельное соединение с backend на каждый запрос и активный SSE дольше минуты. Для GET и HEAD с телом прокси возвращает 400 и закрывает входящее соединение. Регрессия отправляет несколько HTTP-сообщений одним TCP-потоком, включая случай ожидающего предыдущего ответа, и проверяет, что запрос после отказа не дошел до backend. Для методов вне GET, HEAD и POST на `/api/` прокси возвращает 405 с заголовком `Allow`.

В `scripts/qa` сохранены дополнительные HTTP, браузерные и регрессионные сценарии. Браузерным проверкам могут требоваться Playwright и установленный браузер. Для D11/D12 с внешним снимком нужны соответствующая сохраненная версия и исходный PDF, предоставленные оператором. Путь и SHA сверяются при импорте. Скрипты `d11_browser.mjs`, `d11_r1_browser.mjs` и `d12_browser.mjs` работают с уже поднятым отдельным стендом по инструкции локального запуска, используют его `.env.local` и URL из `AIST_QA_WEB_ORIGIN`. Они перезапускают сервисы или управляют сессиями в этом стенде, поэтому запускайте их только на собственной копии снимка. Для автономных проверок чата, редактора и выпуска используйте PostgreSQL-тесты и профили этой страницы.

Автономный Python/TypeScript roundtrip использует checks-образы из раздела сборки. После их сборки выполните `./scripts/roundtrip`. Результаты сохраняются в `.runtime`.

## Работа с настоящим провайдером

Полная последовательность установки с собственным API-ключом, созданием пользователя и настройкой бюджета приведена в [инструкции локального запуска](deployment.md). Репозиторий не предоставляет ключи или доступ к инфраструктуре автора.

Автономные тесты не подтверждают доступность внешней модели, качество ее новых ответов, поведение браузера или отображение документа в Microsoft Word.

## Проверка локального развертывания через интерфейс без OpenAI

Для отдельной пустой установки выполните [инструкцию развертывания](deployment.md) со следующими изменениями:

- В `.local/openai.key` запишите строку `synthetic-local-only`. Настоящий ключ не нужен.
- В `.env.local` выберите отдельное имя стека, например `aist-local-checks`, и свободный порт.
- Вместо функции `aist` из инструкции используйте функцию ниже **во всех командах** запуска, создания пользователя, пересоздания и остановки.

```bash
aist() { docker compose --env-file .env.local -f infra/compose.local.yaml -f infra/qa/compose.local-checks.yaml "$@"; }
```

Повторите миграции, создание логина и настройку доступа. В интерфейсе отправьте без PDF вопрос «Что умеет AIST?», режим ответа выбирается автоматически. Штатный worker и установленный OpenClaw сохранят явно помеченный синтетический ответ. Профиль проверки подменяет только HTTP-подключение к модели, читает синтетический ключ через обычный механизм и проверяет `gpt-6-astra/xhigh/default`. Сети API, worker, БД и исследования изолированы от интернета. Только web, который не получает ключ, подключен также к сети публикации локального порта. Проверка настоящего поиска и платного API здесь невозможна. Модельные строки учета относятся к синтетическим ответам, а не к расходам OpenAI.

Этот профиль предназначен только для отдельной тестовой БД. Для полной записки, исследования и DOCX/PDF на синтетических данных выполните сквозные тесты выше. После проверки остановите свой стек через `aist down`; не переключайте БД с синтетическим учетом на платную эксплуатацию.

### Завершение и восстановление операций

`tests/test_delivery_blockers_postgres.py` проверяет отмену и потерю аренды во время подготовки контекста, ошибку recover, закрытие SSE с несколькими страницами, повторное чтение исходного PDF и восстановление проверенного файла выпуска после сбоя публикации. Для этих проверок нужны изолированная PostgreSQL и закрепленный системный рендер. Холодное восстановление томов и браузерный SSE проверяются в отдельном локальном стеке.

`tests/test_delivery_recovery_postgres.py` проверяет явный повтор выпуска с настоящим рендером и CLI, а также допуск модели и повтор принятой квитанции при недоступном worker. Для проверки сигнала живого worker используйте отдельные процессы API и worker в синтетическом профиле выше: остановите worker, проверьте состояние и новый POST, затем запустите его и повторите тот же запрос.

Сохранность `ownership_review` при независимой модельной правке проверяют `test_note_completeness.py` и `test_draft01_r2_postgres.py::test_unchanged_supported_caption_does_not_block_unrelated_edit`. Прежний разбор владельцев сохраняется только при неизменных разделах владельцев и соответствующих внешних материалах; явный новый разбор проходит обычную проверку.

Цитаты секторов и вспомогательная ссылка на эмитента проверяются в `test_pdf_diagrams.py`, `test_pdf_diagrams_postgres.py` и `test_flow01_04.py`. Извлечение `pdf-lines.v39` разделяет эти фрагменты при проверке расположения, сохраняя исходные цитаты; прежние факты и receipts не переобозначаются, новая версия использует другой ключ извлечения.

Синтетические команды новой записки должны содержать `ownership_review`. Общий помощник `model_save_args` описывает материалы без сведений о владельцах; при наличии материалов темы owners сценарий передает их разбор или конкретные исключения. Неполный сбор с ошибкой отдельного вопроса не разрешает сохранение по ответу на другой вопрос. Проверки сохраняют отказ и историю, а допустимое сохранение выполняют в новом Run по завершенным результатам.

Синхронная оснастка после физического возврата исполнителя вызывает `release_finished`; перед продолжением длительного сценария публикует свежий сигнал своего worker. Это воспроизводит жизненный цикл `Worker.tick`, не отключая busy, TTL и fencing. Граничные сценарии времени явно задают более строгую тестовую политику, проверку общего профиля выполняют отдельно. Лимит визуальных кандидатов проверяется на 65 элементах при разрешенных 64.

Ожидания записок соответствуют `note-technical.v29`: технические ошибки ссылок и финансовых строк блокируют принятие, смысл прозы и заголовков остается `not_checked`. Предупреждения о полноте сохраняются при редактировании; принятие без подтверждения непроверенного смысла и выпуск непринятой версии запрещены.
