# Локальный запуск со своим ключом

Инструкция предназначена для учебной проверки на компьютере проверяющего. Нужны Git, Docker с плагинами Compose и Buildx, `curl`, `openssl`, поддержка Linux amd64 и интернет для сборки, OpenAI и исследования открытых источников. Для Docker рекомендуется выделить не менее 6 ГБ RAM и 20 ГБ свободного диска. На Apple Silicon используется эмуляция amd64, поэтому сборка и первый запуск могут быть медленнее.

Команды рассчитаны на Bash или Zsh в Linux/macOS. В Windows используйте Bash в WSL2 с интеграцией Docker Desktop; клонируйте проект в домашний каталог Linux, чтобы работали Unix-права файлов. Команды не предназначены для прямого выполнения в PowerShell. Перед началом запустите Docker и проверьте инструменты:

```bash
git --version
docker info > /dev/null
docker compose version
docker buildx version
curl --version
openssl version
```

Используйте современный Compose с поддержкой `up --wait`, `init` и `bind.create_host_path`; старый отдельный `docker-compose` не используется.

Интерфейс доступен только на `127.0.0.1`. Это локальный стенд, не инструкция публикации сервиса в интернете. Для удаленного доступа потребуются отдельная настройка HTTPS и защита сервера.

Установка допускает одну активную модельную задачу для всех пользователей и проектов. Пока она выполняется или завершается после отмены, следующая задача получает состояние занятости. Отмена уже отправленного вызова не освобождает слот до физического завершения исполнителя; поздний ответ может повлиять на учет расходов.

## 1. Получить код и подготовить настройки

Если комплект передан локальным архивом, распакуйте его в отдельный каталог и перейдите в корень распакованного проекта. Проверьте состав командой `shasum -a 256 -c SHA256SUMS`, затем начните с `cp .env.local.example .env.local` в блоке ниже. Команды `git clone` и `cd` нужны только при получении предоставленной редакции из GitHub. Архив и состояние ветки GitHub могут различаться; проверяйте манифест именно полученного комплекта.

```bash
git clone https://github.com/AsyncAssassin/aist-analyst-workspace-mipt.git
cd aist-analyst-workspace-mipt
cp .env.local.example .env.local
chmod 600 .env.local
mkdir -m 700 .local
cp executor/openclaw/policy.openai-astra.json .local/policy.json
```

Пока репозиторий приватный, для клонирования нужен предоставленный владельцем доступ GitHub.

В `.env.local` задайте длинный случайный `AIST_DB_PASSWORD`. Пустое значение останавливает Compose до создания контейнеров. Его можно получить командой `openssl rand -hex 24`. Сохраните пароль: при повторном запуске используется прежняя БД. `AIST_STACK_NAME` отделяет контейнеры и тома этой установки от других стендов, `AIST_WEB_PORT` задает локальный порт. Пока оставьте `AIST_CHAT_UI_OWNERS` пустым. Четыре небольшие Docker-подсети используют `AIST_NETWORK_PREFIX` (по умолчанию `10.253.242`, адреса внутри `10.253.242.0/24`). Если диапазон занят Docker, VPN или локальной сетью, выберите свободный частный префикс. Для второй установки нужны отдельные имя стека, порт и префикс.

Создайте собственный ключ на [странице API keys OpenAI](https://platform.openai.com/api-keys) в выбранном API-проекте. Для генерации ему нужен доступ к Responses API. Затем создайте в текстовом редакторе `.local/openai.key`: одна строка с **вашим OpenAI API-ключом**, без кавычек. Только worker получает этот файл как `/run/secrets/openai.key`, только для чтения. `OPENAI_API_KEY` в `.env.local` автоматически не используется. Административный `OPENAI_ADMIN_KEY` не нужен.

```bash
chmod 644 .local/openai.key .local/policy.json
```

Каталог `.local` с правами `700` закрывает файлы от других пользователей компьютера, а права файлов позволяют непривилегированному процессу контейнера прочитать подключенный файл. Не меняйте права каталога на общедоступные. `.local` и `.env.local` исключены из Git и Docker build context. Не добавляйте ключ в исходники, браузер или сообщения об ошибках.

API-проект должен иметь оплачиваемый доступ к `gpt-6-astra` и поддерживать используемые параметры Responses API. Подписка ChatGPT сама по себе не является API-ключом. Профиль приложения закреплен на `gpt-6-astra`, `xhigh`, стандартном режиме; Flex и автоматические повторы выключены. Автоматической замены модели при отсутствии доступа нет.

## 2. Задать предел расходов

В `.local/policy.json` задайте строковыми значениями собственные пределы в USD, например `"80"`. `run.limit` означает поле `limit` внутри объекта `run`:

| Поле | Значение |
| --- | --- |
| `total_authorized_usd` | Общий предел этой установки по всем пользователям и проектам |
| `project_limit` | Предел одного проекта |
| `run.limit` | Предел одной задачи |

В исходном примере общий предел и предел задачи равны `80`, предел проекта равен `200`. Это образец, перед включением генерации выберите приемлемые для себя суммы. Удобно начать с одинакового значения во всех трех полях. До каждого запроса резервируется `24` USD, поэтому меньший доступный остаток блокирует следующий запрос. Для нового извлечения из PDF нужен доступный остаток не менее `48` USD: `24` на извлечение и `24` запаса на последующее завершение. Это проверяется по всем трем денежным ограничениям с учетом уже учтенных расходов. Эти суммы не являются ценой запроса или записки. Многошаговая задача может остановиться по бюджету до сохранения результата.

Поля `quote_usd`, тарифы, `pricing_version`, `budget_scope`, профиль модели и технические ограничения сохраняйте: они закреплены и проверяются кодом. `run.policy_version` обозначает редакцию ваших настроек. При первой установке можно оставить значение из примера; после начала работы при любом изменении `policy.json`, включая бюджет или список пользователей, задавайте новую уникальную версию по [порядку обновления](#изменение-бюджета-и-доступа).

Учет использует сохраненные тарифы, а не читает актуальные цены или баланс OpenAI. Перед платным запуском оператор должен сверить применимость этих тарифов к своему API-проекту. Локальный предел не учитывает запросы других приложений с тем же ключом и не является лимитом счета OpenAI.

Пока оставьте `demo_access.enabled: false` и `owner_ids: []`. Запуск контейнеров, миграции и создание логина не отправляют запросов модели.

## 3. Собрать и запустить

Все дальнейшие команды выполняются из корня репозитория. Сначала соберите базовый backend, затем образ с закрепленными Node и OpenClaw, затем интерфейс:

```bash
docker build --platform linux/amd64 --provenance=false --target runtime -t aist-backend:local -f infra/Dockerfile.backend .
docker build --platform linux/amd64 --provenance=false --build-arg BACKEND_IMAGE=aist-backend:local -t aist-runtime:local -f infra/Dockerfile.openclaw .
docker build --platform linux/amd64 --provenance=false --target runtime -t aist-web:local -f infra/Dockerfile.web .
```

Для сокращения следующих команд определите функцию в текущем терминале:

```bash
aist() { docker compose --env-file .env.local -f infra/compose.local.yaml "$@"; }
aist config --quiet
```

Проверьте чтение ключа и корректность политики тем же пользователем контейнера, который запускает приложение. Эта команда не подключается к OpenAI и не подтверждает действительность ключа:

```bash
aist run --rm --no-deps -T worker python - <<'PYTHON'
import json
from pathlib import Path
from app.config import Settings
from app.normalization import checked
from app.openai_responses import credential
from app.runs import validate_demo_policy

settings = Settings()
credential(settings.openai_secret_path)
policy = json.loads(Path(settings.policy_path).read_text())
checked('BudgetPolicy', policy['run'])
validate_demo_policy(policy)
print('Ключ читается, политика корректна. Запросов к API не было.')
PYTHON
```

После успешной проверки запустите БД, примените миграции и поднимите сервисы. При ошибке остановитесь на текущем шаге и исправьте ее до продолжения:

```bash
aist up -d --wait db
aist run --rm --no-deps -T backend python -m alembic -c /workspace/infra/alembic.ini upgrade head
aist up -d --wait
```

Для обновления существующей установки остановите запись, сохраните резервную копию PostgreSQL и связанных файлов и проверьте восстановление на отдельной копии. Ревизии применяются отдельными транзакциями. При занятой блокировке миграция прерывается через 3 секунды ожидания, текущая ревизия откатывается. Предел выполнения SQL миграции составляет 60 секунд. Устраните причину отказа и повторите `upgrade head` с последней завершенной ревизии.

Создаются PostgreSQL, API, worker, сервис исследования открытых источников и web. Модельные шаги выполняет установленный OpenClaw; ключ остается на стороне AIST. БД и внутренние сервисы не публикуют порты на хосте. Docker-тома хранят БД, PDF, выпуски и состояние исполнителя между перезапусками.

## 4. Создать пользователя и разрешить генерацию

Следующие команды создают логин `examiner` со случайным паролем и сроком действия 30 дней:

```bash
EXPIRY=$(aist run --rm --no-deps -T backend python -c 'from datetime import datetime, timezone, timedelta; print((datetime.now(timezone.utc) + timedelta(days=30)).isoformat())')
aist run --rm --no-deps -T backend python -m app.cli create-login --login examiner --expires-at "$EXPIRY"
```

Команда выводит `user_id`, `login`, `password`, `expires_at`. Сохраните пароль приватно. Повторный запуск с тем же логином не перезаписывает учетную запись. Команды смены пароля и отключения приведены ниже в разделе «Управление логином».

В `.env.local` укажите полученный `user_id`:

```text
AIST_CHAT_UI_OWNERS=usr_полученный_идентификатор
```

В `.local/policy.json` замените только блок доступа, указав **тот же** идентификатор:

```json
"demo_access": {
  "enabled": true,
  "owner_ids": ["usr_полученный_идентификатор"]
}
```

`AIST_CHAT_UI_OWNERS` открывает интерфейс рабочего места, `demo_access` разрешает расходование выбранного бюджета. Для другого проверяющего создайте отдельный логин и добавьте его ID в оба списка. В `AIST_CHAT_UI_OWNERS` перечисляйте ID через запятую **без пробелов**, в `owner_ids` используйте JSON-массив строк; данные пользователей изолированы, общий денежный предел остается общим. Если установка уже использовалась для генерации, изменяйте доступ по [порядку обновления](#изменение-бюджета-и-доступа), включая новую `run.policy_version`.

После сохранения настроек пересоздайте сервисы, чтобы они прочитали новые файлы и переменные:

```bash
aist up -d --wait --force-recreate backend worker
```

## 5. Проверить и отправить задачу

Без модельных запросов:

```bash
aist ps
curl --fail http://127.0.0.1:30811/api/readyz
```

Если меняли `AIST_WEB_PORT`, подставьте его в URL. Откройте [http://127.0.0.1:30811](http://127.0.0.1:30811), войдите созданным логином. Для первого короткого платного запроса отправьте без PDF вопрос «Что умеет AIST?». Режим ответа выбирается автоматически, отдельного пункта «Ответ по источникам» в меню навыков нет. Затем нажмите «Новый чат», загрузите разрешенный PDF через «Файл» → «С компьютера» (без пароля, до 16 МиБ и 40 страниц на файл, до трех PDF в задаче) и отправьте запрос «Подготовь аналитическую записку по прикрепленному PDF». Дождитесь завершения, откройте сохраненную версию и скачайте Word/PDF. Отправка задачи с включенной генерацией расходует средства вашего API-проекта.

Содержимое выбранных PDF и запрос передаются внешней модели. Для проверки можно взять [синтетический PDF из комплекта](../apps/backend/tests/fixtures/flow01/embedded-row-unit.pdf); это искусственные данные, не материал реальной компании. Исследование внешних источников также может использовать сведения из запроса. Используйте материалы, которые разрешено передавать этим сервисам.

Извлечение не гарантирует полноту и точность таблиц, изображений и порядка текста. PDF может содержать скрытый или перекрытый текст, который отличается от видимой страницы и попадает в извлечение. Не считайте визуальное закрашивание удалением сведений. Сверяйте существенные значения и основания с исходной страницей; успешная техническая проверка не подтверждает смысл выводов.

Проверять состояние API нужно через `/api/readyz`: ожидается `"status":"ready"` и `"migrations":"current"`. `aist ps` показывает healthcheck для БД, API и web; у worker и news отдельного healthcheck нет, их состояние `running` само по себе не подтверждает обработку задачи.

| Проблема | Что проверить |
| --- | --- |
| Ошибка отсутствующего bind-файла | Созданы именно файлы `.local/openai.key` и `.local/policy.json`, а не каталоги; команды запущены из корня проекта |
| `Permission denied` при проверке ключа | Права `.local` равны `700`, файлов `644`; в Windows файлы находятся в файловой системе WSL2 |
| Ошибка JSON или политики | JSON без комментариев, числа бюджета записаны строками, остальные поля сохранены из примера |
| Порт занят или подсети пересекаются | Выберите свободные `AIST_WEB_PORT` и `AIST_NETWORK_PREFIX` до запуска; чужие сети не удаляйте |
| API не готов или web отвечает `502` | Проверьте `aist ps`, журналы БД/API и успешность миграций; `config --quiet` проверяет только Compose, не готовность сервисов |
| Неверный пароль или отказ входа | Проверьте логин, срок доступа и состояние учетной записи; при потере пароля используйте команду ниже |
| Интерфейс рабочего места недоступен или генерация выключена | Сверьте один и тот же `user_id` в обоих списках, `enabled: true` и пересоздание backend/worker |
| Недостаточно бюджета | Проверьте остаток общего лимита, проекта и задачи, включая дополнительный запас для извлечения PDF |
| После изменения политики прежний проект отвечает `temporarily_unavailable` | Проверьте новую уникальную `run.policy_version` и пересоздание backend/worker; прежнюю версию нельзя использовать для другого содержимого политики |
| Ошибка провайдера | Проверьте свой ключ, доступ к модели, Responses API и условия API-проекта; локальная проверка ключа не проверяет эти условия |
| Задача остановилась, worker завершился | Проверьте память Docker и `aist ps -a`; состояние задачи и расходы смотрите до повторной отправки |

Не запускайте задачу повторно вслепую: предыдущий запрос мог быть оплачен. Для диагностики: `aist logs --tail=100 db backend worker news web`. Логи и файлы исполнения могут содержать пользовательские материалы, не публикуйте их целиком.

## Диагностика API и worker

Для локального профиля, включая синтетическую проверку интерфейса, используйте функцию `aist` с теми же Compose-файлами и именем проекта, с которыми запускали стенд.

```bash
aist logs --since 15m backend worker
```

Для технического профиля используйте команду `docker compose logs --since 15m backend worker` с его параметрами проекта и файлами Compose. При запуске процессов напрямую запись видна в stderr. Контейнерный вывод читает оператор с доступом к Docker-хосту. Пользователь рабочего места видит в HTTP-ответе код ошибки и `request_id`.

При ответе API 5xx с `ErrorResponse` ищите `api_failure` по этому `request_id`. Запись содержит статус, код и шаблон маршрута или этап проверки сессии. Сбой worker обозначен `worker_failure`. Ищите его по `run_id` и `epoch`, если worker уже знает Run, либо по `worker_id` и этапу. Отказы остановки, восстановления и снимка видны отдельными строками. При неожиданном исключении выводятся класс и ограниченный список кадров с модулем, функцией и номером строки. Содержимое исключения, входные данные и SQL-параметры в эти записи не входят.

`/healthz` показывает, что API отвечает, и возвращает `live_models_enabled` из настроек процесса. Доступность БД и состояние миграций проверяются через `/readyz`. Допуск новой модельной задачи определяется через `/v1/capabilities`. API проверяет сигнал совместимого worker в прикладной PostgreSQL. Сигнал обновляется раз в секунду после прохода рабочего цикла и истекает не позднее 12 секунд после последнего обновления. При штатной остановке worker отзывает сигнал. При невозможности запустить OpenClaw worker отзывает сигнал, продолжает обслуживать выпуск файлов и прекращает брать новые модельные задачи. После исправления причины перезапустите worker. Новый запрос при отсутствии сигнала получает 503; точный повтор принятого запроса возвращает прежнюю задачу.

## Сверка полученных ответов

Worker проверяет сохраненные ответы при восстановлении прерванного Run и при запуске после штатной остановки. Для адресной сверки конкретной задачи выполните команду в worker того же стека. У него есть доступ к БД и тому `execution`, смонтированному в `/data/execution`. В другом профиле используйте каталог `AIST_OPENCLAW_ROOT` того worker, который отправил запрос.

```bash
aist exec -T worker python -m app.cli recover-observed --run "$RUN_ID"
```

Команда читает локальные файлы и БД. Ключ модели и сетевой доступ к провайдерам для сверки не нужны. `recovered` означает, что расход уточнен, а ответ оставлен в истории с подавленной доставкой. `already_accounted` подтверждает существующий учет. При `active` запись остается за действующим исполнителем. `temporarily_unavailable` допускает повтор той же команды. `insufficient_evidence` означает, что исход по имеющимся файлам подтвердить нельзя. Резерв сохраняется. Старые файлы без атомарной отметки в `.received` и ответы без пригодного usage требуют индивидуального основания. Для подтвержденного неоплачиваемого отказа восстановление читает комплект версии 2 и повторно сверяет правило из политики Run.

Публикация результата восстановления в чате, возобновление задачи и повторная отправка из этой команды не выполняются. Прерванный веб-запрос после утраты аренды получает сохраняемый отказ, если его результат не был зафиксирован. Веб-запрос, уже списанный в лимит задачи, остается в счетчике. Повтор по прежним аргументам возвращает зафиксированный результат или отказ.

## Внешнее исследование

News передает Parallel задание и запросы поиска, разрешенный URL и идентификатор корреляции Run. Используйте синтетические или публичные документы. Модель формулирует задание из доступного ей контекста, поэтому ограничение адресов само по себе не фильтрует закрытый текст. Состав исходящих полей, таблицы и тома описаны в [архитектуре](architecture.md#исходящие-запросы-и-сохраненные-материалы).

Том execution и журналы доступны оператору среды и могут содержать текст документов, запросы и результаты. Скрытие чата не удаляет эти данные.

## Управление логином

Если пароль потерян, следующая команда выдаст новый случайный пароль. Старые сессии пользователя будут отозваны:

```bash
aist run --rm --no-deps -T backend python -m app.cli set-password --login examiner
```

Отключение логина и отзыв сессий:

```bash
aist run --rm --no-deps -T backend python -m app.cli disable-login --login examiner
```

Смена пароля не продлевает срок доступа и не включает отключенный логин. Для продолжения после истечения 30 дней или отключения создайте новый логин с другим именем по шагу 4 и добавьте его ID в оба списка. Это новый пользователь с отдельными данными; автоматического переноса прежних проектов нет.

## Изменение бюджета и доступа

1. Завершите или отмените активные задачи через интерфейс и дождитесь завершения выпусков файлов. На время изменения настроек не отправляйте новые задачи.
2. Сохраните приватную резервную копию `.local/policy.json`. Измените нужные пределы или `demo_access`; при добавлении пользователя дополните также `AIST_CHAT_UI_OWNERS` в `.env.local`.
3. Задайте в `run.policy_version` новое, ранее не использованное значение, например `local-review.v1`, при следующем изменении `local-review.v2`. Это поле находится внутри `run`; `pricing_version` и `budget_scope` менять не нужно. Политика сохраняется вместе с проектом, поэтому повторное использование ее версии с другим содержимым блокирует новую задачу в этом проекте.
4. Повторите проверку чтения ключа и политики из шага 3, затем выполните `aist up -d --wait --force-recreate backend worker`. Проверьте `/api/readyz` и доступ пользователя по шагу 5.

Смена версии политики сохраняет прежние расходы и резервы. `total_authorized_usd` задает общий накопленный предел, а не новый остаток. Чтобы запретить следующие генерации, установите `demo_access.enabled: false` и примените новую редакцию тем же порядком. Текущую задачу отменяйте через интерфейс. Уже отправленный запрос модели мог быть оплачен; отмена задачи и отключение доступа не отменяют этот расход.

## Индивидуальная сверка расходов

```bash
run_id=run_00000000000000000000000000000001
call_id=call_00000000000000000000000000000002
aist exec -T worker python -m app.cli billing-call --run "$run_id" --call "$call_id"
aist exec -T worker python -m app.cli billing-call --run "$run_id" --call "$call_id" --evidence /tmp/fixture-billing.json
aist exec -T worker python -m app.cli billing-call --run "$run_id" --call "$call_id" --evidence /tmp/fixture-billing.json --apply
```

Путь к файлу основания в примере указан внутри worker. Для индивидуальной сверки используйте `billing-call` с парой Run/ModelCall. Доступ к команде и БД имеет доверенный локальный оператор. Ключ модели, включенный live-режим и доступ к внешнему API для нее не требуются. Команда просмотра показывает текущий резерв, exposure и состояние транспорта. Укажите `--evidence` для предварительной проверки, затем добавьте `--apply` для записи. Просмотр и проверка выполняются в транзакции только для чтения. Эти действия не запускают `recover-observed`.

Основание в JSON представляет утверждение оператора по окончательному индивидуальному расчету провайдера. Используйте стабильный псевдоним расчетного аккаунта, ссылку на первичный документ в приватном реестре и идентификатор его строки или подтверждения поддержки. `source_sha256` фиксирует заявленный SHA-256 первичного документа. Команда не получает этот документ и не проверяет его подлинность. Оператор подтверждает сумму, принадлежность строки вызову и окончательность расчета, в том числе нулевого. Отсутствие строки в неполной выгрузке оставляет стоимость неизвестной. Сумма за несколько вызовов учитывается отдельно как BillingAggregate и не распределяется по ним.

Возьмите поля привязки и `current_usage_id` из просмотра. Передайте актуальный идентификатор как `expected_usage_id`. Известные идентификаторы провайдера должны совпадать, отсутствующие передаются как `null`. `confirmed_at` содержит время подтверждения в UTC. Передайте USD десятичной строкой с максимум 18 цифрами целой части и 12 знаками после точки. Храните файл основания в приватном каталоге оператора. Пример с синтетическими идентификаторами:

```json
{
  "operation_id": "billing_fixture_01",
  "run_id": "run_00000000000000000000000000000001",
  "call_id": "call_00000000000000000000000000000002",
  "owner_id": "usr_fixture",
  "project_id": "prj_fixture",
  "profile_id": "model_openai-astra-xhigh-v1",
  "provider": "openai",
  "protocol": "https_openai_responses",
  "budget_scope": "openai-authorized-total",
  "account_scope": "fixture-account",
  "provider_request_id": "req_fixture",
  "provider_completion_id": null,
  "source_id": "fixture-statement",
  "line_id": "fixture-line-01",
  "source_sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "subject": "fixture-operator",
  "confirmed_at": "2026-11-12T08:00:00Z",
  "expected_usage_id": "usage_fixture",
  "currency": "USD",
  "amount_usd": "0"
}
```

`recorded` возвращает ID новой строки ledger, `already_recorded` возвращает тот же ID при точном повторе. При потере ответа команды повторите операцию с тем же файлом. Изменение суммы под прежним `operation_id`, повторное использование той же строки основания и устаревший `expected_usage_id` дают конфликт. Для подтвержденной корректировки нужны новое индивидуальное основание, новый ID операции и актуальный `expected_usage_id`. Активный отправленный вызов остается у исполнителя. Сверка наблюдаемого вызова или неизвестного вызова после утраты права отправителя сохраняет транспортное состояние и доставку. Положительный подтвержденный расход может превысить лимит, и следующий допуск учитывает эту сумму.

До отправки достоверно локальный отказ освобождает резерв. Полный пригодный usage дает оценку по закрепленному тарифу. Резерв после HTTP-отказа автоматически снимается только по точному правилу `unbilled_errors` из политики Run и полному сохраненному ответу. Старые политики и текущие примеры дают пустой список. Сам HTTP-статус, неподходящий тип ошибки, оборванный SSE, частичный ответ и потеря связи оставляют стоимость неизвестной при отсутствии пригодного usage. Увеличение лимита дает новый доступный остаток, но не исправляет учет старого вызова. Отсутствие ответа не разрешает повторять запрос, который мог быть отправлен.

## Остановка и сохранность данных

Перед остановкой дождитесь завершения задач и выпусков. После отмены уже отправленный вызов может продолжаться: интерфейс сохраняет занятость до освобождения исполнителя, а поздний ответ учитывается в исходной задаче. `down` и `--force-recreate` останавливают worker и могут прервать текущую генерацию. После перезапуска автоматическое продолжение такой задачи не гарантируется; проверьте ее состояние и учет расходов до повторной отправки.

```bash
aist down
```

Данные остаются в томах. Если пароль БД уже убран из окружения и файла настроек, сохраните прежние имя стека и сетевые параметры. Только для остановки можно выполнить `AIST_DB_PASSWORD=compose-inspection-only aist down`.

Для повторного запуска: перейдите в этот же каталог проекта, снова определите функцию `aist` и выполните `aist up -d --wait`. Не повторяйте шаг 1 поверх существующей установки: `cp` перезапишет ваши настройки. При запуске из другого терминала нужны те же файлы `.env.local` и `.local`. Не меняйте имя стека и пароль БД без переноса данных. После замены ключа повторите предварительную проверку из шага 3 и пересоздайте worker. Для изменения политики применяйте порядок выше.

Команда `aist down --volumes` удаляет данные этой установки, включая учет расходов. Используйте ее только при сознательном полном удалении стенда; это не способ продолжить генерации после исчерпания бюджета.

При обновлении кода сначала завершите активные задачи, выполните `aist down`, повторите три сборки и команды миграции из шага 3, затем `aist up -d --wait`. Существующие настройки и тома сохраните.

### Холодная копия

Источники, прежние версии выпусков и материалы исполнения накапливаются. Скрытие чата не освобождает это место. Проверяйте свободное место на диске Docker и размер томов, включая резервные копии. Автоматическая очистка и квоты диска в этой инструкции не настроены. Не удаляйте отдельные файлы из томов ради освобождения места: история, повторное скачивание и восстановление учета зависят от их сохранности.

Завершите задачи и выпуски, затем выполните `aist stop web worker backend news`. БД нужна для логической копии. Сохраните снимок кода и конфигурацию тарифа отдельно в закрытом месте. В копию не включайте ключ API и файл окружения.

```bash
umask 077
backup=$(mktemp -d)
aist exec -T db pg_dump -U aist -d aist -Fc > "$backup/db.dump"
aist exec -T db psql -U aist -d aist -Atc 'SELECT version_num FROM alembic_version' > "$backup/schema.txt"
aist run --rm --no-deps -T backend tar -C /data -cf - sources exports execution > "$backup/files.tar"
(cd "$backup" && shasum -a 256 db.dump schema.txt files.tar > SHA256SUMS)
```

Восстановите копию на той же версии кода. Определите `aist` с отдельным файлом окружения, новым именем проекта Compose, портом и сетевым префиксом. Подготовьте доступ и политику для восстановленных пользователей. Проверьте суммы `(cd "$backup" && shasum -a 256 -c SHA256SUMS)`. Выполните команды до запуска API и worker, в новой пустой БД и новых томах:

```bash
aist up -d --wait db
aist exec -T db pg_restore -U aist -d aist --exit-on-error --single-transaction < "$backup/db.dump"
aist run --rm --no-deps -T backend tar --no-same-owner -C /data -xpf - < "$backup/files.tar"
aist up -d --wait
```

Сверьте версию схемы, вход и историю, контрольные суммы источника и выпуска, учет и отсутствие нового вызова для завершенных задач. Храните резервную копию закрыто: в ней есть учетные записи, документы и материалы исполнения. Источники с временно недоступным томом можно повторно открыть после его возврата. Проверка исходных размера и SHA восстановит статус той же версии. Для выпуска в состоянии `recovery_required` выполните `aist run --rm --no-deps -T backend python -m app.cli reconcile-export --export-id ID`. Команда проверяет ранее проверенный файл или сохраненный кандидат, не запускает рендер. В DOCX и PDF виден полный заголовок записки до 300 символов. Поле метаданных DOCX содержит до 255 символов.

Для проверки без ключа и расходов используйте [автономные тесты](testing.md). Они подтверждают технический путь на синтетических ответах, но не доступ к внешней модели и не качество новой аналитики.


При таймауте рендера передайте оператору ID выпуска и ревизию сбоя из интерфейса. После устранения причины оператор ставит тот же выпуск в очередь:

```bash
aist run --rm --no-deps -T backend python -m app.cli retry-export --export-id ID --failed-revision REVISION
```

Повтор команды с той же ревизией не запускает вторую попытку. Если после новой попытки получен новый таймаут, сначала разберите причину и используйте ревизию нового сбоя. Для `recovery_required` используйте `reconcile-export`: команда сверит сохраненные байты с прежним SHA. Сбой проверки содержимого не дает права на повтор.
